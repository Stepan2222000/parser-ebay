# План реализации `parser_ebay`

Источник правды — [SPEC.md](SPEC.md). Каждый этап заканчивается терминальной
проверкой на живых базах / тестовом сервере (`144.31.167.227`) — без неё этап
не считается завершённым. Прогоны — и до, и после написания кода этапа.

---

## Этап 1 — База и скелет проекта

**Делаем** (SPEC §8, §11):
- структура репо: `src/`, `migrations/`, `config.yaml`, `.env.example`, `requirements.txt`;
- SQL-миграции: `tasks`, `runs`, `cursors`, `worker_hosts`, `parse_errors`,
  `schema_migrations` — с частичными индексами и уникальным fingerprint среди активных;
- применение миграций при старте (учёт в `schema_migrations`);
- загрузка конфига: `.env` (DSN) + `config.yaml` (параметры, дефолты из SPEC §11).

**Не делаем:** никакой логики задач, браузера, процессов. Только схема и конфиг.

**Проверка:** миграции применяются на `parser_ebay:5420` идемпотентно (повторный
старт — no-op); руками INSERT задач и проверка, что fingerprint-уникальность
и частичные индексы работают как в SPEC §8.

---

## Этап 2 — Очередь и seed (без браузера)

**Делаем** (SPEC §3, §4, §6, §8):
- модуль очереди: вставка по fingerprint (`ON CONFLICT`), забор
  `FOR UPDATE SKIP LOCKED` с приоритетом items-first + порог item-долга (§6),
  статусы/attempts/lease, возврат транзиентных в `pending`;
- разворачивание seed: `purchase_feed(...)` в `ebay_to_buy` → `smart.part_articles`
  → catalog-задачи (§3); запись `runs.articles_total`;
- CLI `start_run` (параметры из SPEC §4: `--zip`, `--product-types`, include-флаги,
  `--no-only-need`) и CLI `set_workers` (§8 `worker_hosts`).

**Не делаем:** воркер-луп, координатор-луп как процессы, браузер, курсоры валидатора.
Seed-разворачивание вызывается пока вручную (функция), не фоновым координатором.

**Проверка:** `start_run --product-types "Для мототехники"` на живых базах →
в `tasks` ровно ожидаемое число catalog-задач (сверить с ручным SQL по
`purchase_feed` × `part_articles`); повторный `start_run` дублей не плодит;
забор задач уважает приоритет и порог долга (создать фейковые item-задачи руками
и убедиться, что catalog не выдаётся).

---

## Этап 3 — Воркер с браузером

**Делаем** (SPEC §7, §2-контракты):
- воркер-процесс: своя Xvfb-сессия по `DISPLAY`-слоту, `cloakbrowser` headed,
  `warmup` один раз, браузер живёт между задачами;
- обработка catalog-задач: пачка до `catalog_batch_size` → `fetch_catalogs`,
  USD-фильтр с логом, `apply_catalog_fetch`, per-query done/failed;
- обработка item-задач: `fetch_item` → `apply_item_snapshot`; при
  `reparse_task_id` — `done_at` в базе валидатора (§5.2, сторона воркера);
- классификация ошибок (§7): транзиентные → pending; `AccessDeniedError` →
  пересоздание браузера; `ParseError` → `failed` + HTML в `parse_errors` (gzip);
  нарушение контракта `ebay_data` → `failed` без ретраев; `max_attempts` → `failed`.

**Не делаем:** супервизор (воркер запускается руками: `python -m ... --slot 0`),
координатор, прокси (`proxy.enabled: false`), route-handler фильтрации.

**Проверка:** на тестовом сервере один воркер съедает реальные catalog-задачи
этапа 2 → `ebay_data` наполняется (сводки `apply_catalog_fetch` в логах),
валидатор сам выносит вердикты; руками вставленная item-задача → PDP-снимок
в `ebay_data`. Замерить фактический темп задач/час на воркер.

---

## Этап 4 — Координатор

**Делаем** (SPEC §5, §9):
- лидерство через advisory lock (один активный на систему, перехват при падении);
- фоновое разворачивание seed-задач (вместо ручного вызова этапа 2);
- курсор `validated_items`: `approved` + `pdp_seen_at IS NULL` → item-задачи,
  перекрытие `cursor_overlap_sec`, сдвиг закладки (§5.1);
- забор `reparse_tasks` пачкой → item-задачи c `reparse_task_id`, прикрепление
  к существующей активной задаче при конфликте fingerprint (§5.2);
- reaper зависших `processing` (§8) и очистка retention (`tasks`, `parse_errors`).

**Не делаем:** супервизор пула, Docker.

**Проверка:** сквозной цикл без ручных вмешательств: `start_run` → каталоги →
валидатор → item-задачи появляются сами → PDP паркуются в `ebay_data`.
Балансировка наблюдаема: при искусственно заниженном пороге долга воркер
переключается на items. Убить процесс координатора — лок подхватывает второй
запущенный экземпляр; убить воркер посреди задачи — reaper возвращает её.

---

## Этап 5 — Супервизор и динамический пул

**Делаем** (SPEC §9):
- супервизор (будущий PID 1): чтение `worker_hosts` по hostname, приведение пула
  к целевому числу — поднятие Xvfb+воркер на свободный слот / SIGTERM лишним
  (доработка текущей задачи, гашение вместе с Xvfb);
- автосоздание строки хоста с `desired_workers_default`;
- graceful shutdown всего контейнера по SIGTERM в пределах `shutdown_grace_sec`;
- координатор-кандидат внутри супервизора.

**Не делаем:** Docker, автоскейл по ресурсам (только ручное `desired_workers`,
автомат — потом со стороны `server_logic`, SPEC §13).

**Проверка:** на тестовом сервере `set_workers` 1→2→0→1 на лету: воркеры
поднимаются/гаснут без потери задач (доработка текущей), Xvfb-процессы не текут;
SIGTERM супервизору — чистый выход всех в пределах grace.

## Этап 6 — Docker-образ и деплой

**Делаем** (SPEC §12, DEPLOY_TEMPLATE.md):
- Dockerfile: python 3.13+, системные библиотеки хромиума явным списком + Xvfb +
  шрифты, `cloakbrowser` с `ensure_binary()` в build-слой, `ebay-library`,
  entrypoint = супервизор;
- `docker-compose.yml` (env из `.env`, рестарт-политика);
- GitHub-репо `Stepan2222000/parser-ebay` (public), GHA workflow →
  `ghcr.io/stepan2222000/parser-ebay`, SSH-деплой в `/root/parser_ebay_app`;
- раскатка контейнера на тестовый сервер.

**Не делаем:** прокси, фильтрация трафика, регистрация в платформе (SPEC §13–14).

**Проверка:** полный цикл этапа 4, но целиком в контейнере на тестовом сервере;
`git push` → образ собрался → задеплоился; `set_workers` управляет пулом
в контейнере; рестарт контейнера не теряет задачи (lease вернёт).

## Этап 7 — Боевой прогон и приёмка

**Делаем:**
- полный запуск на реальном фиде без фильтра категорий (`start_run --zip 19701`);
- наблюдение: темп каталогов/items, item-долг и работа порога (§6), доля
  failed/ParseError, вердикты валидатора, потребление CPU/RAM на воркер
  против норм SPEC §10;
- подстройка дефолтов конфига по фактам (порог долга, batch, таймауты) —
  правкой `config.yaml`, без кода;
- чистка тестовых артефактов (`/root/parser_test` на 144.31.167.227).

**Не делаем:** новых фич. Только наблюдение, твики конфига, фиксация замеров
в SPEC §10.

---

## Вне плана (SPEC §14)

Прокси (`proxymgr`), фильтрация трафика (`ebay_filtering`), несколько zip,
принудительный refresh PDP, регистрация в `server_logic` — отдельными шагами
после приёмки, каждый со своим обсуждением.
