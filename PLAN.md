# План реализации `parser_ebay`

Источник правды — [SPEC.md](SPEC.md). Правило каждого этапа: терминальные
прогоны на живых базах ДО написания кода (прототип в /tmp) и ПОСЛЕ; этап
закрыт только после проверки.

---

## Этап 1 — Схема и FDW

**Делаем** (SPEC §4, §9): миграции `runs` / `tasks` / `parse_errors` со
статусами и частичными индексами; идемпотентный FDW-скрипт (`ebay_fdw`,
`validation_fdw`); загрузка конфига (`.env` + `config.yaml`); CLI-команда
применения миграций (только для разработки — SPEC §4).

**Не делаем:** координатор, воркер, CLI запуска — никакой логики.

**Проверка:** миграции идемпотентны на живой `parser_ebay:5420`; FDW-запросы
к `ebay_data` и валидатору ходят; частичная уникальность fingerprint ведёт
себя по SPEC §3 (активная одна, done-история не мешает).

## Этап 2 — Координатор и CLI

**Делаем** (SPEC §5, §8): цикл координатора целиком — потребности каталогов
(фид × сезонное окно × свежесть), items (`approved` × нет PDP × не мёртв),
reparse, отмена, перевыдача, retention; advisory lock; жёсткие падения;
CLI `start-run` / `stop-run` / `status`.

**Не делаем:** воркер, браузер, Docker. Задачи только появляются и
отменяются — их никто не обрабатывает.

**Проверка:** `start-run` (continuous) → pending совпадают с ручным SQL по
фиду/свежести; `stop-run` отменяет; сезонное окно и дрейф артикулов
отрабатывают; item-задачи рождаются из живых вердиктов валидатора;
перевыдача возвращает искусственно подвешенный processing.

## Этап 3 — Воркер

**Делаем** (SPEC §6): процесс воркера — три колбека + `ebaylib.run_worker`,
cloakbrowser+Xvfb, обёртка смертей (`e.task`, HTML в `parse_errors`);
items-first забор; `done_at` у reparse через FDW.

**Не делаем:** Docker-образ и деплой; прокси и фильтрацию трафика
(SPEC §12); запуск пока руками на тестовом сервере (`144.31.167.227`).

**Проверка:** сквозной цикл без ручных вмешательств: `start-run` → каталоги
→ валидатор → item-задачи → PDP в `ebay_data`, журнал заполняется
(`parse_ms`, attempts); смерть воркера (kill) → перевыдача; SIGTERM →
штатный дренаж; `fetch_item` снятого листинга → `ItemEnded` → потребность
гаснет (SPEC §3).

## Этап 4 — Деплой и боевой прогон

**Делаем** (SPEC §7, §11): Dockerfile (один образ, entrypoint'ы worker /
coordinator, пин `ebay-library`), compose (`restart: always`,
`--scale worker=N`), GHA → ghcr → SSH-деплой; боевой continuous-run на
полном фиде, наблюдение по `status`, подстройка конфига по фактам.

**Не делаем:** ничего из SPEC §12 (прокси, кэш, фото, refresh PDP,
дашборд); регистрацию в server_logic (платформы ещё нет — готовность
обеспечена SPEC §10).

**Проверка:** полный цикл этапа 3, но в контейнерах через ghcr-образ;
рестарт-политика поднимает умершего воркера; масштабирование scale'ом;
темп и `parse_ms` осмысленны в `status`.
